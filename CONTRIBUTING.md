# Contributing

## Before you start

Read the README's [Design decisions and trade-offs](README.md#design-decisions-and-trade-offs)
and [Known limitations](README.md#known-limitations) sections first. A good chunk of "why does
it work this way" is already answered there, and in `docs/adr/` for anything non-obvious enough
to need a longer explanation.

## Setup

```bash
go build ./...
go vet ./...
golangci-lint run   # go install github.com/golangci-lint/cmd/golangci-lint@latest if you don't have it
gofmt -l .           # should print nothing
```

Some tests need real dependencies and self-skip if they're not available:

- `internal/ratelimit` and `internal/cache/exact` want a real Redis at
  `RATELIMIT_TEST_REDIS_ADDR` (defaults to skipping if unset).
- `internal/embedding`, `internal/cache/semantic`, and
  `internal/server`'s semantic-cache tests want `ONNXRUNTIME_LIB_PATH`,
  `EMBEDDING_MODEL_PATH`, `EMBEDDING_VOCAB_PATH` -- `make
  download-embedding-model` fetches the model/vocab; you still need the
  ONNX Runtime shared library for your OS (see `docs/adr/0012`).

Run the full suite with real dependencies wired up before sending a change:

```bash
go test ./... -race
```

## Style

- No comments explaining *what* code does -- names should already say that. A comment earns
  its place only by explaining a *why* that isn't obvious from reading the code: a hidden
  constraint, a workaround for a specific upstream bug, a non-obvious invariant.
- Don't add abstraction, config knobs, or error handling for cases that can't happen. Three
  similar lines beat a premature helper.
- `gofmt` and `golangci-lint run` clean, always.

## Deviating from the README

The README is this project's spec, but it's an illustrative one in places (example configs,
DDL) -- a few real implementation details necessarily differ from it (composite ledger primary
keys for partitioning, config sections the README's example omits, threshold values tuned from
a measured eval set instead of guessed). Every one of those is recorded as an ADR in
`docs/adr/`, referenced from the relevant README section and from `README.md`'s Known
Limitations list. If you're changing behavior the README describes, or making a judgment call
it leaves open, write the ADR: what the README says, what you did instead, why.

## Commit messages

Plain, natural language describing what changed and why it matters -- no AI/tool attribution,
no "Generated by" trailers.

## Pull requests

Include:

- What changed and why (the ADR, if there is one, is often the "why").
- Test coverage for the change -- prefer a real dependency over a mock where one is reasonably
  available in CI (this repo's own tests do this for Redis; see `docs/adr/0015` for how load
  testing does it without a live Postgres).
- Any new `Known limitations` entry the change introduces, however small.
